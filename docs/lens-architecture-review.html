LOD Lens Architecture Review

A structural review of the Lens implementation on feature/lod-lens-selection-lookup, focused on maintainability, ownership boundaries, and simplification opportunities.

Primary theme: simplify ownership Preferred move: one injection model Key fix: session-bound async state Goal: smaller, boring, durable code

Executive summary

The branch adds useful behavior, but the implementation currently spreads responsibility across too many layers.

Current issue: the codebase is supporting both eager manifest injection and background-owned lazy injection for the same runtime.
Preferred direction: inject only a tiny trigger everywhere, then let the background inject the heavy Lens runtime on demand.

That one decision removes a large amount of incidental complexity and gives the feature a cleaner architecture to evolve from.

Top recommendations

  1. Keep only a lightweight trigger script on arbitrary websites.
  2. Make the background worker the canonical owner of heavy Lens runtime injection.
  3. Add a session controller so sentence-mode async work cannot repaint stale UI.
  4. Split the overlay into word mode, sentence mode, render, and shell.
  5. Treat background-bundle.js as a build artifact, not hand-reviewed source.

Diagram 2 — Proposed target architecture

The cleaner “code-judo” version

One injection model, one session model, one persistence boundary. That is the version most likely to stay small and comprehensible.

Why the current branch feels tangled

Finding 1: heavy scripts are globally injected even though the background already knows how to inject them on demand.
Finding 2: sentence-mode actions perform async work against mutable shared state without a strong session boundary.
Finding 3: lens-overlay.js has become shell + renderer + controller + state manager + persistence orchestrator.
Finding 4: a generated background-bundle.js is now checked in and normalized into the review surface.

Concrete simplification moves

Move 1: keep only selection-trigger-lite.js on arbitrary sites.
Move 2: let background-lens.js own all heavy runtime injection.
Move 3: create lens-session.js so async completions can be ignored when stale.
Move 4: split sentence mode and rendering out of the overlay shell.

How stale async work should be contained

Suggested module boundaries

selection-trigger-lite.js

Selection heuristics, Luxembourgish page hints, floating button, background message dispatch.

background-lens.js

Command handling, context menu, on-demand injection, approved API proxying.

lens-runtime.js

Entry point for opening the overlay and creating a session.

lens-word-mode.js

Single-word lookup, candidates, suggestions, save-state synchronization.

lens-sentence-mode.js

Tokenized lookup, candidate resolution, per-word save toggles, bulk actions.

lens-render.js

Pure rendering helpers or DOM patch functions. No fetches. No store writes.

lens-session.js

Session ids, stale async invalidation, active session checks, guard helpers.

Migration plan

  1. Simplify injection first. Remove the heavy Lens runtime from all-sites manifest injection. Keep only the trigger globally injected.
  2. Add a session boundary. Convert sentence-mode async actions to require an active session before they mutate state or repaint.
  3. Split the overlay. Extract sentence mode first, then extract rendering, then reduce the shell to a thin coordinator.
  4. Clean up bundle ownership. Treat background-bundle.js as a generated build artifact rather than authored source.
The most important structural simplification is step 1. It removes the architectural overlap that currently makes the feature harder to reason about.
