Quiz

Goal: make the boundary feel obvious, not memorized.

1) Which part of LODVault reads the user’s selected text from the page?

2) Why is it risky to think of this feature as “the page just fetches the LOD API directly”?

3) In the actual LODVault design, which context owns the privileged network fetch to https://lod.lu/api/*?

4) Which manifest capability makes that remote fetch path legitimate in this repo?

5) What changes in sentence mode?

6) Which hardening step best improves the current proxy design?

Trace the code yourself

Open each file and answer the prompt before moving on.

  1. scripts/selection-trigger.js — Find where the selected text is normalized and where lodvault:open-lens-overlay is sent.
  2. scripts/background-impl.js — Find where the lens scripts are injected and where lodvault:lens-fetch is handled.
  3. scripts/lens-lookup.js — Find runtimeProxyFetch() and getFetchImplementation(). Ask: why does this prefer messaging over direct fetch?
  4. scripts/lens-overlay.js — Find openWordMode() and openSentenceMode(). Ask: where does the overlay stop being UI and start delegating to lookup?
  5. manifest.json — Confirm the exact host permission that legitimizes the background fetch path.
Mini-check: if you can explain those five files in one paragraph, you probably understand the core architecture.

Scenario challenge

Imagine a refactor: someone removes runtimeProxyFetch() and changes the lens code to always use globalThis.fetch from the tab context.

Write 4–8 sentences answering:

  • What architectural boundary got blurred?
  • What kind of browser restriction becomes relevant again?
  • Why is the current design safer to maintain?
  • What hardening would you add to the current background proxy?
Rubric
  • A strong answer says the privileged network boundary moved from the background back into the tab/page-side environment.
  • It mentions same-origin policy and CORS as the browser restriction that becomes relevant again for cross-origin reads.
  • It explains that the current design keeps selection-reading and network privilege separate.
  • It proposes URL validation / allowlisting in the background message handler as the next hardening step.
