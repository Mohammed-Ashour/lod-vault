LODVault teaching note · selected-text lookup

How LODVault avoids cross-origin trouble when you select text and look up LOD data

The key idea is simple: the extension reads the selected text in the page, but it does not trust the page context to fetch the LOD API. Instead, it routes those requests through the extension background service worker, which has explicit host_permissions for https://lod.lu/api/*.136

Working assumption for this explainer: you want to understand the selected-text lookup path well enough to safely maintain or extend LODVault’s lens flow.

The content script notices the selection.
selection-trigger.js normalizes text and sends lodvault:open-lens-overlay.7
The background injects the lens.
background-impl.js loads the overlay and lookup helpers into the current tab.9
The overlay starts a lookup.

The lookup layer chooses the background proxy.
getFetchImplementation() returns runtimeProxyFetch when runtime messaging is available.8
The background fetches LOD.
The onMessage handler receives lodvault:lens-fetch and performs fetch(message.url).9
The overlay renders the result.
The returned JSON becomes a resolved entry, candidates, or suggestions in the lens UI.10

Sentence route

A multi-word selection is treated as a sentence.
lens-overlay.js switches into sentence mode when lookup.isSentence(query) is true.10
The sentence is split into word tokens.
lookup.lookupSentence() normalizes, splits, then loops over word tokens.8
Each word still uses the same proxy fetch path.
So sentence mode changes volume, not architecture: more lookups, same boundary.810
The overlay renders per-word status.
Resolved words, ambiguous words, suggestions, and errors are rendered per token.10

Why this avoids cross-origin pain

What would go wrong if the page did the fetch?

If a script running as part of the page tries to fetch https://lod.lu/api/..., the browser treats that as a normal cross-origin web request. Whether JavaScript can read the response depends on the server’s CORS policy.45

That is a fragile architecture, because your feature becomes dependent on remote server headers from the point of view of an arbitrary website.

What changes when the background does the fetch?

Chrome extension docs are explicit: content scripts are still subject to same-origin rules, but extension service workers can talk to remote servers when the extension has the right host permissions.1

LODVault declares https://lod.lu/api/* in host_permissions, then performs the fetch in the background service worker.69

Security footnote worth noticing

A background proxy avoids page-context cross-origin problems, but it introduces a different design concern: the background should not become a generic fetch proxy for arbitrary URLs.1

Chrome’s own guidance warns against letting content scripts request any URL they want. In this repo, the background currently fetches message.url directly when it handles lodvault:lens-fetch.9

Good next hardening step: validate that requested URLs are restricted to the exact LOD API endpoints this feature needs, instead of trusting any URL passed through the message.
